Purpose and scope
These are the standards this team's Rust projects follow: idiomatic code, a stable public API, and a repository that verifies its own claims within the limits of its tools. Meeting them is a requirement of the project, not a universal certificate of production readiness. Sections 1 to 6 describe how to write Rust; sections 7 to 10 describe how to keep a Rust project healthy over time. Rules a tool can check are checked in CI; contracts, architecture decisions and justifications are checked in review, and tests and tools are evidence within their own limits, not proof.
Rules apply to libraries and binaries alike unless a rule says otherwise. Where a rule leaves a choice open, clarity for the next reader wins.
Rule strength and scope. Must defines an obligation; should defines the default, and a deviation from it is justified in writing. Unless marked, a rule is a should. Scope, the kind of project a rule applies to (published library, binary, async service, crate with unsafe, no_std), is stated separately, at the top of each section or on the rule itself; a rule can be a must that applies only to published libraries. Security obligations are must wherever they appear and are marked as such: secrets never reach logs, errors or Debug output; an operation whose safety depends on preconditions the interface cannot guarantee is never presented as safe; invalid external input never panics.
Exceptions. An exception to a should records the requirement it serves and the trade-off accepted, in the code (reason = "...") or in the PR description. A must is not waived for convenience.
Project stack. Crates named in this document (thiserror, anyhow, tracing, proptest, insta, criterion, cargo-deny) are this project's chosen tools, not properties of Rust. A different tool with the same guarantees is an acceptable substitute; the rule is the property, not the crate.
1. Tooling and CI
rustfmt is the formatting authority and Clippy is part of the workflow; both run in CI, or they are only intentions. Scope: every crate.
• rustfmt. A rustfmt.toml is committed at the workspace root. CI runs cargo fmt --all --check. Formatting is never discussed in code review.
• Clippy. CI runs cargo clippy --workspace --all-targets --all-features --locked -- -D warnings. Warnings are errors; a warning that survives to main is a bug in the pipeline. --all-targets selects targets, not packages: --workspace is what checks every member, whatever default-members says.
• Lint configuration lives in Cargo.toml under [workspace.lints], and every member opts in with [lints] workspace = true; without that line the member inherits nothing. Enable clippy::pedantic selectively, not wholesale.
• Every #[allow(...)] carries a reason, enforced by clippy::allow_attributes_without_reason: #[allow(clippy::too_many_arguments, reason = "mirrors the C ABI")]. Prefer #[expect(..., reason = "...")] where the MSRV allows it (1.81+): it warns when the suppression is no longer needed.
• Baseline lint set for every crate: unsafe_op_in_unsafe_fn = "deny", clippy::undocumented_unsafe_blocks = "deny", missing_docs = "warn" (libraries), clippy::unwrap_used and clippy::expect_used (libraries; section 4 says what they cover).
• Toolchain policy. rust-toolchain.toml pins the toolchain used for development, rustfmt and Clippy, so -D warnings means the same thing on every machine and in CI. It is updated on a schedule (each stable release, or quarterly) in its own PR, which is also where new lints are triaged. The MSRV (section 7) is a separate, older version tested in its own job.
• CI also runs the test configurations in section 8, RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked (broken intra-doc links fail the build; --all-features so that APIs behind optional features are documented and their links checked too), and the dependency checks in section 9.
• --locked has a scope. Builds, tests, lints and docs that verify the committed dependency graph use --locked, and the commands in this document show it. Jobs that update dependencies or deliberately modify manifests (the fresh-resolution job in section 9; cargo hack --no-dev-deps in section 8) run in an isolated checkout without it and state their lockfile policy.
2. Types and invariants
Use the type system to represent invariants, so that an invalid state cannot be constructed rather than merely checked. Parse, don't validate: validate once at the boundary and produce a type that carries the proof. Scope: every crate.
• Prefer enum, Option and Result to implicit state. A bool plus an Option plus a comment is an enum waiting to be written. (Enum versus trait object for a set of implementations: section 6.)
• Newtypes for domain values. UserId(u64), Meters(f64), NonEmptyVec<T>.
• Every path that constructs or modifies a value preserves its invariants. Validation is centralized in the constructor and the mutating methods, and no public path bypasses it. Deserialization is such a path: where a derived Deserialize would skip the check, deserialize an intermediate representation and convert through a validated TryFrom (#[serde(try_from = "...")]), or implement Deserialize by hand.
• Privacy by default. Fields that carry an invariant are private; pub(crate) and private modules are the default, pub is a decision. An invariant enforced in a constructor is void if the field is pub.
• Typestate and generics have a cost. Encode a state machine in types when the states are few and the transitions matter (a builder, a connection lifecycle). When the type signature becomes harder to read than the runtime check it replaces, use the runtime check. Section 6 governs.
• Make illegal states unrepresentable, not merely rejected, when a representation allows it: struct NonEmptyVec<T> { first: T, rest: Vec<T> } cannot be empty, by construction, with no check anywhere. When no such representation exists, a checked constructor is the right tool.
• Sensitive values get a type (must). Passwords, tokens and keys live in a wrapper (secrecy::SecretString or an in-house equivalent) whose Debug does not expose the content and whose Display, when implemented at all, does not either, so they cannot leak through logs, panics or error messages by accident.
3. Ownership and function signatures
Ownership is intentional: every clone(), Rc, Arc and lifetime is a decision the author can defend, not a reflex to silence the borrow checker. Scope: every crate.
• Clone is a decision, not a sin. Arc::clone, a small String cloned once during setup, or a Copy type are fine. Contorting lifetimes for hours to avoid a clone that never shows up in a profile is not. When unsure, write the clone. A comment is warranted only for a known, measured cost, and a performance claim points at a benchmark (section 8).
• Own what you must, borrow what you can. A function takes &T unless it stores or consumes the value. Small Copy values (integers, bool, char, small Copy structs) are passed by value: attempts: u32 needs no justification, attempts: &u32 does, and clippy::trivially_copy_pass_by_ref flags the latter. Store owned data in structs unless the struct is explicitly a view.
• Generous inputs, concrete outputs. Accept &str over String, &[T] over Vec<T>, impl AsRef<Path>, impl AsRef<str>, impl IntoIterator<Item = T>. Return a concrete type when callers benefit from knowing it; return impl Trait when hiding the concrete type is the point (iterators, futures and closures are the common cases, an implementation you intend to swap is another). The question is what the API needs to expose, not which category the value falls in.
• Prefer &str, &[T] and &T over &String, &Vec<T> and &Box<T> in signatures. The borrowed view is what nearly every caller can provide and nearly every callee needs. Take the container itself only when a container property (capacity, shrink_to_fit) is what the function is about.
• Interior mutability is a boundary, not a habit. RefCell, Cell and Mutex appear where shared mutation is the design, and the type's documentation says why.
• Lifetimes in public types are a commitment. A struct Parser<'a> forces every holder to manage 'a; prefer owning the input unless zero-copy is the point of the type.
4. Errors, panics and effects
APIs make errors and effects explicit in their signatures: a function that can fail returns Result, a function that does I/O says so in its name or its type, and a function that can panic documents when. Scope: every crate; the error-type split is library versus application.
Errors
• Libraries expose typed errors by default. An enum per module or per operation, implementing std::error::Error, Display and Debug, with source() wired to the underlying cause. thiserror is this project's way to write them; hand-written impls are fine.
• Applications use anyhow (this project's choice; eyre is equivalent) at the top level and add context with .context("...") at every boundary where the caller would otherwise not know what was being attempted.
• Box<dyn Error> in a library's public API is a deliberate choice, not the default. It supports downcast_ref, so callers can still inspect it, but it gives up exhaustive matching and makes the set of failure modes invisible in the signature. Use it when the error set is open or uninteresting to callers, and say so in the docs.
• Error messages are lowercase, without trailing punctuation, and do not repeat their source. The chain is printed by the caller: failed to open config: permission denied.
• Error messages and Debug output never contain secrets (must; section 2, sensitive values). An error that wraps a request does not embed the authorization header.
• #[non_exhaustive] on error enums that will gain variants; section 7 says when that trade-off is worth it.
• ? over match for propagation; map_err only when the conversion adds information.
Panics
• unwrap() and expect() are allowed when they represent a real invariant (the value was validated above), or in code where a panic is the correct outcome (tests, examples, build scripts, main of a CLI after argument parsing).
• expect messages describe the invariant, not the failure: expect("index was bounds-checked by the caller"), never expect("failed").
• In libraries, clippy::unwrap_used and clippy::expect_used are on so every unwrap and expect is a visible, justified allowance. These lints find explicit calls only: indexing, integer overflow in debug builds, RefCell::borrow and todo!() panic without them. They make panics reviewable, not absent.
• Every public function with a known panic path has a # Panics section in its doc comment. Callers may read a missing section as "no panic on valid input"; that is the standard the author writes to, and review checks the section against the code.
• Never panic on invalid input from outside the process. That is an error, returned as one.
Effects
• Functions that read the clock, the environment, randomness or the filesystem take those as parameters or traits where testability matters; hidden globals make code untestable and order-dependent.
• #[must_use] where ignoring the value is almost certainly a bug: builders, guards, pure functions. Section 7 has the rule; Result already carries it.
5. Unsafe
unsafe is permitted, but every use is small, justified, documented and encapsulated. Scope: crates containing unsafe. The documentation and soundness rules below are must; the tool choices are should.
• Every unsafe block carries a // SAFETY: comment (must) stating why each precondition of the operation holds at that point. clippy::undocumented_unsafe_blocks enforces presence, for blocks and impls alike; whether the argument is true is review's job.
• Every unsafe fn documents its contract (must) in a # Safety section: what the caller must guarantee. An unsafe trait the project defines documents, on the trait, what an implementor must guarantee.
• Every unsafe impl carries a // SAFETY: comment (must) stating why the type satisfies the trait's contract. unsafe impl Send and unsafe impl Sync are the common cases: the comment names the invariant that makes the type safe to share, and review checks that no field or method breaks it.
• unsafe_op_in_unsafe_fn is denied (must) so an unsafe fn body still marks each unsafe operation individually.
• Prefer a safe API; expose an unsafe one only when the interface cannot establish the preconditions. A safe wrapper is right whenever it can guarantee every precondition of the unsafe core; then the core is private, as short as possible, and does one thing. When safety depends on guarantees the caller must provide and the signature cannot express (std::slice::from_raw_parts is the canonical case), expose an unsafe fn with its # Safety contract. What is never acceptable (must): presenting as safe an operation whose safety depends on preconditions the interface does not guarantee.
• Prefer a well-audited crate (bytemuck, zerocopy) over hand-rolled transmutes and pointer casts.
• Miri runs in CI for every crate containing unsafe (cargo +nightly miri test), on the tests and targets it supports. Miri checks the executions the tests actually take; it does not prove an API sound, and its support for FFI and platform-specific operations is limited, and it does not support every target. The crate records what Miri could not cover (a SAFETY.md, or a section in the crate docs), and that gap is closed by the SAFETY arguments and review, not waived.
• #![forbid(unsafe_code)] in crates that have no reason to use it, so its introduction is a deliberate, reviewable change.
6. Abstraction and composition
Prefer traits and composition to artificial hierarchies, and be suspicious of an abstraction that has fewer than three concrete uses. DRY loses to clarity whenever the abstraction makes the code harder to read. Scope: every crate.
• Traits describe capabilities, not taxonomies. trait Storage with Read/Write methods, not trait Animal with Dog: Animal. Rust has no inheritance; do not simulate it with default methods and Deref.
• A closed set of implementations is an enum, not a trait object; reach for dyn Trait when the set is open (plugins, user-provided callbacks) or when erasing the type is the point. Static dispatch by default; dyn when it cuts compile time or binary size measurably, or when heterogeneity is required.
• Three uses is a heuristic, not a gate. Duplication is cheaper than the wrong abstraction, and two similar functions are fine. But a domain boundary, a substitution contract (a trait the tests fake) or a public extension point can justify an abstraction at its first use. Either way the abstraction must be simpler than the sum of what it replaces.
• Generic parameters earn their place at the interface. A bound is justified when it lets callers pass more kinds of value at no cost to them (impl AsRef<Path>, impl IntoIterator), or when the crate needs it internally. A generic that exists only so the repository's one call site compiles is a concrete type in disguise; for a public API, count the callers you cannot see.
• Macros are the last resort: after functions, generics and traits have failed to remove the duplication. A macro_rules! is documented like a public function and has tests.
7. Public API surface
Everything pub in a library is a contract: it is documented, it interoperates with std, and changing it follows semver. Derives, bounds, field visibility and trait impls are all part of that contract. Scope: published libraries in full; internal crates and binaries take the documentation rules and skip the semver machinery.
Documentation
• Every public item has a doc comment: what it does, its errors (# Errors), its panics (# Panics), its safety contract (# Safety) and the invariants it maintains. #![warn(missing_docs)] enforces presence; review enforces substance.
• Doctests cover the main flows and every non-trivial operation (# Examples). This is the normative rule; section 8 and the checklist refer to it. Doctests compile and run in CI, so an example that does not compile is a documentation bug. A getter, a constant or an enum variant does not need an artificial example to satisfy a count.
• The crate root has a //! overview: what the crate is for, the two or three entry points, and a minimal example.
Interoperability with std
• Implement Debug on every public type: derived where the fields are plain data, by hand where the type holds a secret, or a field that is huge or meaningless when printed. A Debug that prints a credential is a leak (section 2).
• Derive Clone, PartialEq, Eq, Hash, PartialOrd, Ord, Default, Copy when semantically correct. Never derive Ord or Hash on a type containing floats; never derive Copy on a type that may grow.
• Implement Display for user-facing values and From/TryFrom for conversions (never Into directly). For a collection, implement IntoIterator on the forms whose iteration is defined (T, &T, &mut T) and Iterator on the iterator types they produce, not on the collection itself.
• FromStr is a separate contract from Display. Display may be lossy or incomplete by design. Implement FromStr where parsing is meaningful, and promise parse(display(x)) == x only when the type documents that round-trip; then test it (section 8).
• AsRef and Borrow are different promises. AsRef<T> says "you can view me as a T". Borrow<T> additionally guarantees that Eq, Ord and Hash agree between the owned and borrowed forms, which is what lets a HashMap<String, _> be queried with a &str. Implement AsRef for a plain view; implement Borrow only when that equivalence holds.
• Public types are Send + Sync unless there is a documented reason. Assert it in a test: static_assertions::assert_impl_all!(Client: Send, Sync);
• serde support goes behind a serde feature when serialization is an integration rather than the crate's purpose. A crate that is about a wire format, or that already depends on serde for its own reasons, implements the traits unconditionally.
Semver discipline
• #[non_exhaustive] is a decision about how the type will evolve, not a default attribute. Put it on enums and structs you expect to grow, so adding a variant or field stays a minor change. Leave it off when exhaustive matching by callers is part of the type's value (a small, stable set of states); then adding a variant is a major, and that is the intended trade-off.
• What is and is not breaking, in outline. Adding a variant to an exhaustive public enum: major. Adding a public field to a struct whose fields were all public and that is not #[non_exhaustive]: major, because it breaks struct-literal construction and exhaustive patterns outside the crate; with a private field already present, or under #[non_exhaustive], it can be minor if the other contracts hold. Adding a private field to a struct that already has at least one: minor, as long as the new field does not change the struct's auto traits (Send, Sync) or its Copy-ness. Removing a public trait implementation, or changing what it guarantees: major, whether the impl was derived or written by hand; the contract is the impl, not the attribute. Tightening a bound: major. Loosening a bound or generalizing a signature: usually minor, but not always, because generalizing can break type inference at call sites; treat it as a change to check, not a free pass. The Cargo reference's semver chapter provides detailed guidance; this paragraph is an outline of it.
• #[must_use] on builders, constructors, pure functions, guards and handles: anywhere ignoring the value is almost certainly a bug. Not on every function.
• cargo semver-checks runs in CI on every PR against the last release. It complements the semver review; it does not replace it. Its own documentation lists categories of breakage it does not yet detect (some trait and generic changes among them), and the reviewer owns those.
• MSRV is declared in Cargo.toml (rust-version = "1.xx"), tested in CI on that exact toolchain, and raised only in a minor release with a changelog entry. The development toolchain (section 1) is a separate, newer version.
• A CHANGELOG.md in Keep a Changelog format, updated in the same PR as the change.
8. Testing
Every invariant the type system cannot express is covered by a test; a rule a tool can check is checked in CI, and a rule only review can check is written so a reviewer knows what to look for. Scope: every crate; property, snapshot, fuzz and Loom tests where the risk named below exists.
• Unit tests live in a #[cfg(test)] mod tests at the bottom of the file they test and may reach private items. They test behavior, not implementation: a refactor that preserves behavior should not require changing a test's expectations, even when it means updating a call to a renamed private function.
• Integration tests live in tests/ and use only the public API. They are the executable definition of what the crate promises.
• Doctests follow the rule in section 7: main flows and non-trivial operations, compiled and run in CI.
• Property-based tests (proptest or quickcheck) for anything with an invariant: parsers, serializers, arithmetic, collections, state machines. A round-trip property like parse(display(x)) == x is tested where the type promises it (section 7), not assumed for every Display.
• Snapshot tests (insta) for large structured output: error messages, generated code, rendered templates.
• Fuzzing (cargo-fuzz) for parsers and decoders that take untrusted input; Loom for lock-free or otherwise delicate concurrent code. Neither is required of every crate; both are required where that risk exists.
• Every bug fix adds a test that failed before the fix. The test's name or comment references the issue.
• Unit tests are hermetic and deterministic. No wall-clock sleeps, no network, no shared mutable global state; time, randomness and I/O are injected (section 4, Effects). Integration and end-to-end suites may talk to real dependencies, under isolation the test controls (a container, a fixture server, a temp directory) and never to shared production systems.
• A flaky test is a bug with an owner. It is investigated the day it flakes, then fixed or quarantined with a named owner and a deadline (#[ignore = "flaky: issue #123, owner @x, until 2026-10-15"]). It is not retried until green, and it is not deleted to make CI pass.
• Three configurations run in CI, all with --workspace --locked: default features, --no-default-features, and --all-features. Users mostly run the default; the two extremes do not test it. Feature combinations that matter beyond these get a cargo hack --feature-powerset job.
• Published libraries in a workspace are also checked per package. Cargo unifies features across a build: a workspace binary that enables the library's serde feature makes --no-default-features compile the library with serde anyway, hiding a missing cfg or a missing dependency. cargo hack check --each-feature --no-dev-deps -p <lib> builds each library on its own with each of its features, and runs for every crate this workspace publishes.
• Benchmarks (criterion or divan) exist for any code path where performance is a stated requirement, and a claim like "no clone here for performance" points at one.
9. Dependencies and features
Every dependency is a liability the project takes on deliberately: it is audited on entry, pinned where it must be, and checked continuously. Scope: every crate.
• Adding a dependency is a reviewed decision. The PR says what it replaces and why writing it in-house is worse. Prefer crates that are widely used, actively maintained, and have few transitive dependencies of their own.
• Cargo.lock is committed for binaries and, following the Cargo team's current recommendation, for libraries too; verification jobs run with --locked.
• Test against fresh resolutions, too. --locked tests the frozen graph a binary ships with. A scheduled job runs cargo update and the full test suite, so a library's users, who resolve their own graph, are not the first to find a broken minor release of a dependency. Updates land as their own PR (Dependabot/Renovate, or that monthly job).
• cargo deny check runs in CI: license allowlist, advisory database (RustSec), duplicate-version detection and a source allowlist. cargo audit alone is the minimum if cargo deny is not adopted.
• Features are additive. Enabling a feature does not remove existing functionality or break public API and behavior contracts; it may add functionality, including new diagnostic output. Supported features stay compatible when enabled together; a feature that breaks another is a bug.
• default features are minimal. A library's default set is what nearly every user needs and nothing more; serde, tokio, tracing and similar integrations are opt-in when they are optional integrations; section 7 says when they are not.
• No wildcard versions (*); use caret requirements ("1.4") and let the lockfile pin. Exact pins ("=1.4.2") only with a comment explaining the breakage they avoid.
• Workspace dependencies ([workspace.dependencies]) are the single place a version is declared in a multi-crate workspace.
10. Async hygiene
Async code follows the same rules as everything above, plus a small set that exists because a future is code that pauses. Scope: async services and async libraries. The Send and 'static requirements below come from the executor, not the language; they are stated for this project's executor, Tokio's multi-threaded runtime.
• Never block inside a runtime. No std::thread::sleep, no synchronous file or network I/O, no CPU-heavy loop inside an async fn. Use the runtime's async equivalents, or move the work to spawn_blocking (or a dedicated thread pool). Moving it is not the whole answer: work handed to spawn_blocking has a bounded completion or a cooperative cancellation signal when it needs one, because abort does not interrupt a blocking task that has started, and shutdown will wait for it, or time out and abandon it still running. CPU-heavy work runs under an explicit concurrency limit (a semaphore or a dedicated pool), not one blocking task per request.
• Send and 'static follow the spawn API, not a universal rule. tokio::spawn requires the future and its output to be Send + 'static; spawn_local and LocalSet accept !Send futures; a scoped or single-threaded executor has its own rules. Design types for the API the code actually uses (Arc where a task crosses threads; Rc is fine on a LocalSet), and document which one that is.
• Avoid holding a synchronous lock guard across an .await, whether or not the guard is Send. Being able to move a guard between threads does not remove the risk of blocking the executor or deadlocking: std::sync::MutexGuard is !Send and tokio::spawn rejects it, but parking_lot's guard is Send with its send_guard feature and compiles fine, and the deadlock is the same. Release the guard before the await, or restructure so the critical section contains no await. When the section must span an await, tokio::sync::Mutex exists for exactly that: it is the exception, chosen knowingly, because it is slower; its guard is Send when T: Send.
• Cancellation is a normal event. A future may be dropped at any .await; never assume code after an await runs. Spawning does not make work complete: the runtime drops pending tasks on shutdown. Work that must finish has an owner that awaits it, an explicit cancellation policy (what is rolled back, what is retried), and a place in the shutdown sequence (a CancellationToken or equivalent, plus a bounded grace period). A Drop guard restores an invariant; it does not finish I/O.
• Structured concurrency over fire-and-forget. A spawned task has an owner that awaits or aborts it (JoinSet, a scoped task API). Detached tasks are documented as such, with their shutdown behavior.
• Library APIs name their runtime contract. tokio::io::AsyncRead and futures::io::AsyncRead are different traits; taking one does not make an API runtime-agnostic, it chooses a side. A library either states the runtime it targets, or exposes a trait of its own and ships adapters behind features (tokio; smol for the futures-based ecosystem). async-std is discontinued (RustSec advisory, August 2025) and appears only as a legacy integration.
• Limits are explicit and stated as behavior. Every outbound call has a timeout. Every queue, channel and buffer that receives external input is bounded, and the code documents what happens at the bound: reject, drop oldest, or apply backpressure to the producer. Request size, concurrency and connection counts have configured limits. An unbounded channel is a decision with a documented reason and a documented risk.
• Instrument with tracing (this project's choice) so spans follow tasks across awaits; log and println! lose that context. Two operational rules come with it. Never hold the guard from Span::enter() across an .await, or events from other tasks get attributed to the wrong span; use #[instrument] or .instrument(span) for async code. And review what #[instrument] captures: arguments are recorded by default, so skip(...) or skip_all with explicit fields(...) keeps request bodies and credentials out of the trace (section 2, must).
Checklist
Two lists: what a new crate sets up in its first commit, and what a reviewer checks because no tool can. A reviewer does not re-certify what a required CI job already verifies, and a line here summarizes the rule in the body without making it stricter; where the body allows a documented exception, the check is that the exception is documented.
New crate: first commit
1. rustfmt.toml at the workspace root; cargo fmt --all --check in CI.
2. [workspace.lints] with the baseline set; [lints] workspace = true in every member.
3. Clippy in CI: --workspace --all-targets --all-features --locked -- -D warnings.
4. rust-toolchain.toml pinned; rust-version declared and tested in its own job.
5. Three test jobs, all --workspace --locked: default, --no-default-features, --all-features.
6. cargo hack check --each-feature --no-dev-deps for every library the workspace publishes, in an isolated checkout without --locked.
7. RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked; doctests run.
8. Cargo.lock committed; cargo deny check (or at least cargo audit) in CI; a scheduled fresh-resolution job with its lockfile policy stated.
9. cargo semver-checks in CI (published libraries).
10. Miri job for every crate with unsafe, with what it cannot cover recorded; #![forbid(unsafe_code)] where there is none.
11. CHANGELOG.md created; default features minimal.
Review: what CI cannot check
1. Construction, mutation and deserialization all preserve invariants, through a validated constructor or a representation that is valid by construction; no pub field bypasses them.
2. Every clone, Arc, RefCell and public lifetime is a defensible decision.
3. Inputs are borrowed views (&str, &[T], impl AsRef) or small Copy values, and owned where the function stores or consumes the value; outputs are concrete unless hiding the type is the point.
4. The error strategy follows section 4: typed errors by default, Box<dyn Error> only as a documented choice; messages lowercase, chain-friendly, and free of secrets.
5. Every unwrap/expect names a real invariant or sits where a panic is the deliberate outcome (section 4); # Panics sections match the code.
6. Every unsafe block's and unsafe impl's // SAFETY: argument is true, not merely present; nothing is presented as safe on preconditions the interface cannot guarantee.
7. Abstractions are simpler than what they replace; generics earn their place at the interface.
8. Docs have substance; doctests show the main flows; Debug impls and #[instrument] captures leak nothing.
9. Semver: the change's category is named in the PR; #[non_exhaustive] is used as a decision.
10. Tests test behavior; a bug fix carries its failing-then-passing test; flaky tests have an owner and a deadline.
11. A new dependency says what it replaces and why.
12. Async: no blocking calls, no sync guard across .await; every task has an owner or a documented detached policy; every external queue is bounded, or its unbounded choice is documented with its risk; blocking work follows the completion, cancellation and shutdown policy of section 10.
13. Any exception to a should records its requirement and the trade-off accepted.
